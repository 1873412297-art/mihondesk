# 数据库升级快照与恢复

当 mihondesk 打开旧结构数据库、即将执行结构迁移时，会先把一致性快照保存在
当前配置目录的 `database/migration-backups/` 下。文件名类似
`library.db.v1-to-v3-<唯一编号>.db`。只有校验完整性、确认原结构版本、刷新文件并
完成原子重命名后，迁移才会开始。快照包含 SQLite WAL 中已提交的数据。

新数据库、当前结构的数据库，以及被拒绝的未知/较新结构，不会生成这些快照。
应用版本更新但数据库结构不变时，也不会生成快照。快照不会自动覆盖或删除；
一次失败后的重试可能产生新的独立快照。它们是本机数据库文件，不是可通过
“导入备份”读取的 `.tachibk`，也不包含扩展 APK、图片、下载文件和独立配置文件。

## 升级失败

如果无法保存快照，升级不会开始。正常界面启动会显示原因类别、检查磁盘空间和
目录写入权限的提示及目录位置；后台命令返回非零退出码及
`DATABASE_SNAPSHOT_FAILED`，不会弹出需要人工关闭的窗口。

迁移本身失败时，数据库事务会尝试回滚，已经完成的快照仍然保留。错误信息给出
快照位置。先保存错误日志并检查存储问题，不要删除数据库来强行启动。
快照既有旧结构也有旧数据；恢复会放弃快照之后的数据库更改。

## 使用快照恢复

1. 退出 mihondesk，确认没有正在执行的后台更新、备份或其他使用该配置目录的进程。
2. **先复制整个配置目录到新的安全位置**，保留现有 `library.db`、`library.db-wal`、
   `library.db-shm`、`library.db-journal`（存在时）和 `migration-backups`，不要覆盖旧副本。
3. 在新的独立配置目录中建立 `database` 子目录，把选定的完整 `.db` 快照复制为
   `database/library.db`。不要把原数据库的 WAL/SHM/journal 文件混入这个新目录。
4. 使用 `mihondesk.exe --data-dir="<新配置目录的绝对路径>" --list-library-json` 检查。
   新版本会再次生成自己的迁移前快照并尝试迁移。命令成功后，用相同的 `--data-dir`
   启动界面确认漫画、分类、阅读进度和历史。此独立目录验证不会替换原配置目录。
5. 如需恢复到原配置目录，保持所有相关进程关闭，把原 `database` 目录完整移动到
   一个未使用的保留位置，再建立新的 `database` 目录并放入已验证的快照，命名为
   `library.db`。这样不会遗留旧数据库的日志文件。原配置、扩展和媒体文件保留原位。

若迁移仍然失败，应保留原目录、快照和日志处理故障。不要反复覆盖原数据。
快照不是应用安装包回滚机制；旧版程序也可能不理解新版本的其他配置内容。

实现依据：[SQLite VACUUM INTO 文档](https://www.sqlite.org/lang_vacuum.html)。它生成
逻辑一致的数据库副本，并非原文件逐字节复制。当前实现还会校验并刷新快照文件；
不承诺故障硬件或所有文件系统下的断电持久性。
